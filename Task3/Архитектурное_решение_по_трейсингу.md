# Задание 3. Архитектурное решение по трейсингу

## 1. Мотивация
Трейсинг необходим для того, чтобы отслеживать жизненный цикл заказа, проходящего через микросервисы (Онлайн-магазин -> CRM -> RabbitMQ -> MES). Текущая проблема с потерей заказов решается крайне долго, так как команде не хватает контекста.
**Метрики, на которые повлияет решение:**
* **Технические:** Снижение MTTR (Mean Time to Recovery) при расследовании инцидентов; уменьшение количества ошибок интеграции в RabbitMQ.
* **Бизнес-метрики:** Снижение количества жалоб от B2B/B2C клиентов на зависшие заказы; повышение лояльности пользователей; снижение нагрузки на первую линию поддержки.

## 2. Покрытие трейсингом
**Системы для покрытия:**
1. Backend Онлайн-магазина (загрузка моделей, формирование корзины).
2. Backend CRM (процессинг заказов, взаимодействие с B2B API).
3. Интеграционный слой RabbitMQ.
4. Backend MES (расчет стоимости, статусы производства).

**Данные в трейсе:** 
`order_id`, `user_id` (или `client_id`), таймстемпы изменения статусов заказов, `trace_id` для связывания спанов. Места возможной "поломки": отправка и чтение сообщений из RabbitMQ, длительная транзакция расчета стоимости в MES.

## 3. Предлагаемое решение
**Технологический стек:** OpenTelemetry (генерация трейсов) + Jaeger (хранение и UI).
**Реализация:**
* В сервисах (Java Spring Boot и C#) подключается OpenTelemetry SDK для автоматического и ручного инструментирования.
* Трейс начинается на входе запроса в Онлайн-магазин или API.
* При отправке сообщения в RabbitMQ контекст трейса (`trace_id`, `span_id`) передается в заголовках (headers) сообщения. Консьюмеры на стороне CRM и MES извлекают этот контекст и продолжают трейс.
* Данные о трейсах асинхронно отправляются в OpenTelemetry Collector, откуда экспортируются в Jaeger.
* *Схема:* Добавляется компонент Jaeger и OpenTelemetry Collector. Связи от бэкендов направляются к коллектору. (Изменения выделяются на C4 диаграмме красным цветом).

## 4. Компромиссы
* **Высокая нагрузка:** Если количество заказов B2B огромно, запись 100% трейсов создаст оверхед на сеть и хранилище. Потребуется настройка семплирования (sampling, например, 10-20% успешных запросов и 100% запросов с ошибками).
* **Проприетарность MES:** Так как MES был куплен готовым (хоть и с исходниками), внедрение SDK внутрь монолита C# может оказаться нетривиальным из-за legacy кода или отсутствия DI (Dependency Injection), что сделает реализацию более дорогой.

## 5. Безопасность
* **Защита доступа:** Jaeger UI разворачивается во внутреннем VPN компании. Доступ предоставляется только инженерам и специалистам поддержки по ролевой модели (RBAC) через SSO (корпоративные учетные записи).
* **Обезличивание данных (Data Masking):** В трейсы строго запрещено передавать персональные данные (номера карт, ФИО, пароли). SDK должны быть сконфигурированы на фильтрацию PII. Для идентификации используются только суррогатные идентификаторы (UUID).

## 6. Дополнительное задание: Автоматический мониторинг и алертинг
На основе данных трейсинга можно настроить **Trace-based metrics**. 
* **Как реализовано:** OpenTelemetry Collector с плагином `spanmetrics` или Jaeger/Prometheus связка. На основе длительности спанов для расчетов MES генерируются метрики. Если заказ находится между спанами `SUBMITTED` и `PRICE_CALCULATED` дольше SLA (например, 30 минут), срабатывает алерт.
* **Схема:** Добавляется связь между Jaeger/OTel Collector и Alertmanager (выделено зеленым цветом на финальной C4 диаграмме).
