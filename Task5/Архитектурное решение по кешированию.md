# Архитектурное решение по кешированию

## Что кешируем

Основной кандидат на кеширование - первая страница MES, где оператор видит список заказов в работе по статусам. Именно на неё жалуются операторы, и именно она влияет на скорость взятия новых заказов в работу. Фильтр и пагинация не помогли, значит проблема, вероятно, в повторяющихся чтениях из MES DB, сортировке по новым заказам и расчёте агрегатов по статусам.

Кешировать тяжёлый расчёт стоимости 3D-модели как первый шаг не предлагаю. Расчёт зависит от содержимого файла, сложности модели, производственных параметров и может занимать до 30 минут. Его лучше сначала перевести в асинхронную очередь с воркерами и сохранять результат расчёта в MES DB как доменное состояние заказа. Кеш расчёта можно добавить позже только для полностью идентичных файлов по `model_hash` и версии алгоритма расчёта.

В область кеширования на первом этапе входят:

- список новых и активных заказов для MES-дашборда по статусам;
- счётчики заказов по статусам для первой страницы MES;
- карточка краткой информации по заказу, если она часто открывается операторами;
- справочники MES, которые редко меняются: статусы, типы изделий, производственные участки.

Не кешируем:

- изменение статуса заказа как источник истины;
- персональные данные клиента;
- платежные данные;
- содержимое 3D-файла;
- данные, по которым оператор должен видеть строго подтверждённую запись, если заказ только что был изменён текущей операцией.

## Мотивация

Кеширование должно решить две практические проблемы:

- ускорить первую страницу MES для операторов;
- снизить нагрузку повторяющихся чтений на MES DB, чтобы база не мешала расчёту цены и изменению статусов.

Операторам важно видеть самые новые заказы, потому что от этого зависит, кто возьмёт заказ в работу. Поэтому кеш должен быть не «долгим снимком на несколько минут», а короткой read-моделью, которая обновляется при изменении заказа и быстро отдаёт отсортированные списки.

Ожидаемый эффект:

- p95 загрузки MES-дашборда меньше 1 секунды;
- меньше slow queries на MES DB;
- стабильная работа дашборда при росте заказов;
- меньше конфликтов за новые заказы;
- меньше жалоб операторов и меньше ручных обращений к разработчикам.

## Предлагаемое решение

### Тип кеширования

Используем серверное кеширование в MES backend. Клиентское кеширование для первой страницы MES не подходит как основное решение: операторы должны видеть свежие заказы, а разные операторы работают с одним общим пулом. Браузерный кеш может показать устаревший список и усилить конфликт за заказ.

Кеш размещаем в Redis. MES API остаётся единственной точкой доступа к данным для фронтенда и сам решает, когда читать из Redis, когда идти в MES DB и когда обновлять кеш.

Дополнительно создаём read-модель для дашборда:

- `mes:orders:list:{status}:{page}` - список order id и кратких полей, отсортированный по `created_at desc`;
- `mes:orders:counts` - счётчики по статусам;
- `mes:order:summary:{order_id}` - краткая карточка заказа;
- `mes:dict:*` - редкие справочники.

Источник истины остаётся MES DB. Redis - ускоряющий слой, потеря Redis не должна приводить к потере заказов.

### Паттерн

Для чтения списка заказов используем Cache-Aside:

1. MES API получает запрос дашборда.
2. Проверяет Redis по ключу `status + page + page_size + sort`.
3. При попадании возвращает данные из кеша.
4. При промахе читает MES DB, кладёт результат в Redis с коротким TTL и возвращает ответ.

Для записи изменения статуса используем запись в MES DB и программную инвалидацию/обновление связанных ключей:

1. MES API валидирует переход статуса.
2. В транзакции меняет статус в MES DB и записывает событие `OrderStatusChanged`.
3. После успешного commit удаляет или обновляет ключи списков старого и нового статуса.
4. Обновляет счётчики по статусам.
5. Публикует событие для CRM/RabbitMQ.

Почему Cache-Aside:

- прост в реализации для текущей команды;
- Redis можно потерять без потери данных;
- легко включать постепенно: сначала дашборд, потом карточки и справочники;
- хорошо подходит для чтений, где источник истины - БД.

Почему не Write-Through как основной паттерн:

- он усложнит каждую запись статуса: нужно синхронно писать и в БД, и в кеш;
- ошибка Redis начнёт влиять на критичный путь смены статуса;
- для списков по статусам всё равно нужны дополнительные операции перестановки заказа между наборами.

Почему не Refresh-Ahead как основной паттерн:

- сложно заранее знать, какие фильтры и страницы реально откроют операторы;
- можно тратить ресурсы на прогрев неиспользуемых комбинаций;
- риск вернуть устаревшее состояние выше, если прогрев отстаёт от реальных изменений.

Refresh-Ahead можно добавить позже только для первого экрана: например, заранее обновлять `MANUFACTURING_APPROVED` и `PRICE_CALCULATED` page 1 каждые 10-15 секунд, если метрики покажут, что этого не хватает.

### Диаграмма последовательности

```mermaid
sequenceDiagram
    autonumber
    actor Operator as Оператор MES
    participant MesUi as MES UI
    participant MesApi as MES API
    participant Redis as Redis cache
    participant MesDb as MES DB
    participant Rabbit as RabbitMQ
    participant Crm as CRM API

    rect rgb(238, 246, 255)
        Operator->>MesUi: Открывает дашборд со статусом
        MesUi->>MesApi: GET /orders?status=PRICE_CALCULATED&page=1
        MesApi->>Redis: GET mes:orders:list:PRICE_CALCULATED:1
        alt cache hit
            Redis-->>MesApi: Список заказов и updated_at
            MesApi-->>MesUi: 200 OK, orders, cache=hit
        else cache miss
            Redis-->>MesApi: nil
            MesApi->>MesDb: SELECT orders WHERE status ORDER BY created_at DESC LIMIT ...
            MesDb-->>MesApi: Список заказов
            MesApi->>Redis: SET key TTL 30s
            MesApi-->>MesUi: 200 OK, orders, cache=miss
        end
        MesUi-->>Operator: Показывает новые заказы
    end

    rect rgb(242, 255, 242)
        Operator->>MesUi: Берёт заказ в работу
        MesUi->>MesApi: PATCH /orders/{id}/status MANUFACTURING_STARTED
        MesApi->>MesDb: BEGIN; validate transition; UPDATE order; INSERT status_event; COMMIT
        MesDb-->>MesApi: Commit OK
        MesApi->>Redis: DEL list keys for old/new statuses
        MesApi->>Redis: SET mes:order:summary:{id}; UPDATE counters
        MesApi->>Rabbit: Publish OrderStatusChanged
        Rabbit-->>Crm: Consume OrderStatusChanged
        Crm-->>Rabbit: ACK
        MesApi-->>MesUi: 200 OK, new status
        MesUi-->>Operator: Заказ закреплён за оператором
    end
```

### Инвалидация кеша

Основная стратегия - программная инвалидация по ключу после успешной записи в MES DB. Для списков заказов удаляем ключи старого и нового статуса, потому что заказ исчезает из одного списка и появляется в другом. Для карточки заказа обновляем `mes:order:summary:{order_id}`. Для счётчиков по статусам обновляем значения атомарно или пересчитываем при следующем чтении.

Дополнительно используем короткий TTL:

- списки заказов: 30 секунд;
- счётчики по статусам: 15-30 секунд;
- карточка краткой информации: 60 секунд;
- справочники: 1-24 часа в зависимости от частоты изменений.

Комбинация программной инвалидации и TTL защищает от двух сценариев: после записи кеш быстро очищается, а если инвалидация не прошла из-за временной ошибки Redis, устаревший ключ сам исчезнет.

Сравнение стратегий:

| Стратегия | Подходит? | Почему |
| --- | --- | --- |
| Только TTL | Нет как основная | Простая, но оператор может до 30 секунд видеть заказ не в том статусе после изменения |
| Инвалидация по ключу | Да | Позволяет сразу убрать устаревшие списки после смены статуса |
| Программное обновление кеша | Частично | Хорошо для `order:summary` и счётчиков, но сложнее для страниц списков с сортировкой |
| Инвалидация по событию | Да на втором этапе | Если появится отдельный consumer событий статуса, он сможет обновлять read-модель асинхронно |
| Полная очистка кеша | Нет | Слишком грубая, создаст всплески нагрузки на MES DB |

### Конкурентность и консистентность

Чтобы два оператора не взяли один заказ, кеш не должен быть механизмом блокировки. При нажатии «взять в работу» MES API делает условное обновление в БД:

```sql
UPDATE orders
SET status = 'MANUFACTURING_STARTED', operator_id = :operator_id
WHERE id = :order_id
  AND status = 'MANUFACTURING_APPROVED';
```

Если обновлена 0 строк, значит заказ уже взял другой оператор или статус изменился. API возвращает конфликт `409`, UI обновляет список. Так источник истины остаётся в БД, а кеш только ускоряет чтение.

### Отказоустойчивость

- Если Redis недоступен, MES API читает из MES DB и пишет метрику/лог `cache_unavailable`.
- Для Redis включаем managed Redis или Redis Sentinel/Cluster, persistence не обязателен для всех ключей, потому что данные восстанавливаются из MES DB.
- Вводим таймаут на обращение к Redis 50-100 мс, чтобы кеш не замедлял API.
- Ограничиваем размер значений: списки содержат только поля для дашборда, полная карточка берётся отдельным запросом.
- Добавляем защиту от cache stampede: request coalescing или короткий distributed lock на прогрев ключа.

### Метрики кеша

- `mes_cache_hit_ratio` по типу ключа;
- `mes_cache_request_duration_seconds`;
- `mes_cache_errors_total`;
- `mes_dashboard_duration_seconds` с label `cache=hit|miss|bypass`;
- `mes_cache_invalidations_total`;
- `mes_db_dashboard_query_duration_seconds`;
- `mes_dashboard_conflict_total` для попыток взять уже занятый заказ.

Целевое состояние:

- cache hit ratio для первого экрана выше 80%;
- p95 MES-дашборда меньше 1 секунды;
- p95 обращения к Redis меньше 50 мс;
- отсутствие роста конфликтов операторов после включения кеша.

## План внедрения

1. Измерить текущие slow queries MES-дашборда и добавить индексы `status, created_at desc`, если их нет.
2. Подключить Redis в release и production окружениях.
3. Реализовать Cache-Aside для списка заказов по статусу и первой страницы.
4. Добавить программную инвалидацию после смены статуса.
5. Включить метрики hit ratio, latency, invalidations и p95 дашборда.
6. Провести нагрузочный тест с ростом заказов и несколькими операторами.
7. Включить кеш в production постепенно через feature flag: сначала для одного статуса, затем для всех статусов дашборда.
