# Задание 2. Выбор и настройка мониторинга в системе

## 1. Мотивация
Внедрение мониторинга позволит команде проактивно выявлять сбои (до массовых жалоб клиентов и API-партнеров), измерять реальную нагрузку на систему и понимать её пределы. Это критически важно для сокращения Time-to-Resolve (MTTR) и обоснования ресурсов на инфраструктуру. Без метрик любые решения по оптимизации будут приниматься вслепую.

## 2. Выбор подхода к мониторингу
Для системы будем использовать комбинацию подходов:
- **RED (Rate, Errors, Duration)** — для микросервисов, веб-приложений и API (Онлайн-магазин, CRM backend, MES backend).
- **USE (Utilization, Saturation, Errors)** — для инфраструктурного слоя (инстансы EC2, managed базы данных, RabbitMQ).

## 3. Выбор метрик

### Для микросервисов и API (RED подход):
* **HTTP Request Rate (RPS)**
  * *Зачем:* Оценка общей нагрузки и выявление спайков (особенно от API-пользователей).
  * *Ярлыки:* `service_name`, `endpoint`, `http_status`.
* **HTTP Error Rate**
  * *Зачем:* Отслеживание процента ошибок для быстрого реагирования на инциденты.
  * *Ярлыки:* `service_name`, `endpoint`, `error_code`.
* **HTTP Response Time / Latency**
  * *Зачем:* Выявление медленных запросов, влияющих на пользовательский опыт (например, долго грузящийся дашборд MES).
  * *Ярлыки:* `service_name`, `endpoint`.

### Для инфраструктуры (USE подход):
* **Утилизация CPU / Памяти (CPU / Memory Utilization)**
  * *Зачем:* Контроль за потреблением ресурсов приложениями на EC2.
  * *Ярлыки:* `instance_id`, `service_name`.
* **RabbitMQ Queue Depth (Длина очереди)**
  * *Зачем:* Помогает выявить «застрявшие» заказы между CRM и MES (очередь растет, если консьюмеры не справляются или упали).
  * *Ярлыки:* `queue_name`.
* **Database Query Latency & Connections (Задержка запросов БД и пулы соединений)**
  * *Зачем:* Выявление долгих запросов (от дашборда) и исчерпания пула коннектов при росте заказов.
  * *Ярлыки:* `db_name`, `query_type`.

## 4. План действий (Драфт ТЗ)
1. Развернуть и настроить инстанс Prometheus (Time-series DB) для сбора метрик.
2. Развернуть Grafana и подключить Prometheus как источник данных.
3. Добавить инструментирование метрик:
   - Внедрить `Prometheus-net` для MES (C#).
   - Внедрить `Micrometer / Spring Boot Actuator` для CRM и Онлайн-магазина (Java).
4. Настроить Prometheus Node Exporter на EC2 инстансах и интеграцию с Yandex Cloud Monitoring для БД.
5. Создать базовые дашборды в Grafana (по сервисам и инфраструктуре).
6. Настроить алертинг на аномальные показатели (Alertmanager).

## 5. Показатели насыщенности (Saturation)
* **CPU Utilization > 80%** в течение 5 минут на EC2 инстансе.
  * *Действие:* Отправить алерт в Telegram/Slack канал дежурным DevOps/разработчикам. Запустить пайплайн масштабирования (добавление нового инстанса EC2 в балансировщик).
* **RabbitMQ Memory limit reached (срабатывание Memory Alarm)**.
  * *Действие:* Завести highest-приоритет тикет, отправить алерт, так как брокер блокирует публикацию новых сообщений (прямая потеря новых заказов).
* **Database Connection Pool Utilization > 90%**.
  * *Действие:* Алерт бэкенд-инженерам (возможность утечки коннектов или неоптимальных долгих транзакций).
